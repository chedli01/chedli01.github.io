**I designed and implemented KubeForge**, a locally tested Kubernetes self-service prototype for creating **logical development environments within an existing shared cluster**. Developers request an environment through a single declarative `DevEnvironment` YAML manifest; Crossplane provisions and reconciles the namespace, resource policies and access controls behind that request.

## The engineering challenge

A Kubernetes development environment needs much more than a namespace: it also needs resource limits, access permissions and networking boundaries. Requiring developers to maintain each low-level manifest introduces repeated work and configuration mistakes. **My goal was to turn environment creation into a controlled, self-service platform capability.**

## 1. Designing the platform API

I designed a new **`DevEnvironment` declarative resource** by extending the Kubernetes API with a **Crossplane v2 CompositeResourceDefinition (XRD)**, which generates the corresponding CRD. One high-level YAML specification expresses the desired developer environment without exposing the individual Kubernetes objects that implement it.

The result is a developer-facing contract: **request an environment, not eight separate resources**.

## 2. Building provisioning and reconciliation

I personally designed and implemented the **Crossplane Composition using Go templating**, mapping each `DevEnvironment` composite resource (XR) into **eight native Kubernetes resources**:

- **Namespace**, **ResourceQuota** and **LimitRange** for isolation and resource constraints.
- **Two Roles**, **ServiceAccount** and **RoleBinding** for role-based access.
- **NetworkPolicy** for network boundaries.

Crossplane's reconciliation loop handles **initial provisioning, updates and drift correction**. This was an implementation in **Crossplane Go templating**, not a Go backend service.

## 3. Enforcing validation before GitOps synchronization

I developed a **Python validator** that checks the **YAML syntax**, **XRD schema** and **platform-specific rules** of incoming `DevEnvironment` manifests.

I integrated that validator into **GitHub Actions CI triggered by pull requests**. If a manifest is noncompliant, a **required check fails and blocks the merge** to the protected `main` branch. After a valid request is merged, I configured **Argo CD** to synchronize the accepted manifests from Git to Kubernetes.

This creates a clear delivery boundary: **validate and review requests first; reconcile the approved desired state afterward**.

## 4. Proving the platform works end to end

I developed and ran a **10-stage automated E2E suite** that tests actual platform behavior—not simply YAML formatting—including:

- Provisioning of all expected resources and enforcement of quotas.
- RBAC authorization and generated network-policy configuration.
- Configuration updates and correction of configuration drift.
- Environment deletion and lifecycle cleanup.

**All 10 out of 10 E2E stages passed**, tested on a local four-node kind cluster. The network-policy stages validated generated rules and reconciliation, rather than packet-level traffic isolation.

## What I contributed

KubeForge brings together **API design, infrastructure abstraction, automated guardrails, GitOps and behavioral testing**. I owned the high-level API, Composition implementation, Python validation pipeline, Argo CD configuration and E2E verification to build and verify a working local self-service platform prototype.
