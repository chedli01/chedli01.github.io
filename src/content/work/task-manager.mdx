**I designed and implemented two distinct Azure deployment strategies** for the same application: a **cost-conscious single-VM setup** and a **scalable AKS platform**. I used Infrastructure as Code and automation throughout, then added monitoring, GitOps delivery and controller-level troubleshooting to make the environments reproducible and operable.

[![Animated Task Manager architecture showing the Azure VM deployment and CI/CD delivery path](/images/task-manager.gif)](/images/task-manager.gif)

*My animated diagram illustrates the single-VM strategy and its CI/CD flow. The AKS architecture and GitOps workflow are detailed below.*

## 1. Choosing infrastructure to match the workload

I designed a **Terraform-based Azure architecture** with two approaches rather than assuming Kubernetes was always necessary:

- **Single VM:** a lower-cost Linux environment using **Docker Compose and Ansible** to run the application stack.
- **Azure Kubernetes Service (AKS):** a more scalable, cloud-native platform for higher workloads, with **Helm, GitOps and cluster observability**.

The key engineering decision was to separate the **application's delivery needs** from the **complexity and cost of its deployment platform**.

## 2. Provisioning and configuring the VM environment

I provisioned the Azure VM with **Terraform**, then created **idempotent Ansible playbooks** to configure Linux and deploy **Nginx, backend services, PostgreSQL and Prometheus/Grafana**.

This approach makes both infrastructure creation and application setup reproducible instead of dependent on manual server configuration.

## 3. Building the AKS platform and its observability

I provisioned **AKS using Terraform**, including **VNet and NSG** configuration. I automated deployment of **Nginx Ingress, Argo CD and kube-prometheus-stack using Helm**.

For observability, I configured **Prometheus ServiceMonitor** to collect application metrics and visualized them in **Grafana dashboards**. I also used **Kustomize base/overlays** to separate shared Kubernetes resources from environment-specific configuration.

### AKS, GitOps and service-mesh architecture

[![AKS architecture diagram showing Terraform provisioning, GitHub Actions CI, Git manifests, Argo CD App-of-Apps, Helm-managed services, Kubernetes workloads, Prometheus and Grafana, HPA and Linkerd mTLS](/images/task-manager-aks-gitops.svg)](/images/task-manager-aks-gitops.svg)

*AKS delivery and operations architecture — the second deployment strategy alongside the VM animation above.*

I also configured **Linkerd as a Kubernetes service mesh**, providing **automatic mutual TLS (mTLS) for traffic between meshed services** without requiring changes to application code. Linkerd is integrated into the platform's Argo CD application hierarchy alongside the workloads and observability components.

## 4. Delivering code through CI and pull-based GitOps

I built an end-to-end workflow in which **CI builds and tags Docker images with the commit SHA**, updates deployment manifests in Git, and **Argo CD pulls and synchronizes the desired state** to the cluster. Importantly, GitHub Actions runners do **not** require access to the cluster credentials to perform deployment.

The implementation achieved an **approximately 5-minute code-to-deployment cycle**.

## 5. Solving a real controller reconciliation issue

I diagnosed an **Argo CD / Horizontal Pod Autoscaler (HPA) conflict**: Argo CD was continuously reverting the `replicas` value after HPA adjusted it to match CPU/memory usage.

I fixed the reconciliation loop by configuring Argo CD to **ignore the `replicas` field** during synchronization, allowing HPA to control scaling without GitOps overwriting the live replica count.
