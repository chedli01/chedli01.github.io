**I built a controlled Azure subscription provisioning workflow** that turns structured requests into **reviewable Infrastructure-as-Code changes**. Rather than manually creating and placing each subscription, the workflow connects an internal request process to **Terraform and GitLab CI/CD**, while preserving the required **billing and Management Group associations** and a deliberate approval step before applying changes.

## 1. Connecting subscription requests to Terraform

Requests submitted through an **internal dashboard** are persisted as **YAML**. I implemented the flow that passes those request parameters through **GitLab CI/CD** to a **dedicated Terraform module based on `azurerm_subscription`**.

The module provisions a subscription under the appropriate **Microsoft Customer Agreement (MCA) billing scope** and associates it with the requested **Azure Management Group**. Both are important: billing scope determines the financial context, while Management Group placement determines where the subscription fits in the Azure governance hierarchy.

## 2. Implementing reviewable, controlled provisioning

I used **GitLab CI/CD** to orchestrate the provisioning lifecycle:

1. **Validate** the Terraform configuration.
2. **Plan** the proposed infrastructure changes and expose them for review.
3. **Wait for manual approval** before applying the plan.
4. **Apply** the reviewed change using **service-principal authentication**.

**The workflow does not auto-apply subscriptions just because a YAML request exists.** The manual gate is an intentional part of the design.

## What I contributed

I connected **declarative YAML requests, a dedicated Terraform provisioning module and approval-oriented GitLab automation** into a repeatable subscription-creation process. The result demonstrates practical **Infrastructure as Code, Azure governance and controlled cloud automation**, without claiming an unverified scale or speedup.
